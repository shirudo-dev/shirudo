shirudo architecture
====================

This document describes the implemented design: what runs where, which
kernel mechanisms carry the enforcement, what state a target holds, and
how artifacts, packages and telemetry move.  The code is authoritative;
when this document and the code disagree, the code is right and this
document has a bug.  The security argument behind the design is in
`threat-model <threat-model.rst>`__, the byte-level artifact format in
`upatch-spec <upatch-spec.rst>`__, and the export path in
`telemetry <telemetry.rst>`__.

1) What shirudo is
------------------

shirudo is a BPF security platform.  It ships BPF live patches
("upatches") to Linux targets, and it makes sure a target runs only the
BPF its operator signed.  Both halves are needed: a patching mechanism
any root process can use is an attack surface, and an enforcement
mechanism without a way to ship fixes is a wall nobody can work behind.

Once ``shirudo init`` has run, the kernel accepts BPF programs from
userspace only through signed loader programs.  A loader is a
``BPF_PROG_TYPE_SYSCALL`` program generated by libbpf's gen_loader on
the operator; it embeds the ``bpf()`` calls that create the maps and
load the payload program.  The operator CMS-signs the loader
instructions and data with an ML-DSA-87 key.  The target kernel
verifies that signature at ``BPF_PROG_LOAD`` against the certificate in
the sealed bpf keyring, before the verifier and before any LSM hook
runs.  The payload program is hash-locked to the loader
(``excl_prog_hash``), so a signature over a few kilobytes of loader
covers every instruction that ends up attached.

Everything else follows from that.  The kernel-side enforcement is a
set of BPF LSM programs that shirudo loads through the same signed
path.  Every state change extends a per-boot TPM measurement register
anchored in a PCR, so an operator predicts from the signed set what a
target must report and has the TPM certify that it does.
The userspace side is one binary with git-like subcommands; on the
target there is no daemon and no socket, only one-shot invocations
driven by systemd timers.

2) Why shirudo exists
---------------------

The kernel's CVE stream runs at dozens of fixes a day, and that churn
is not going to end.  The distribution model of enabling every Kconfig
option for compatibility and then carrying a kernel that deviates from
upstream stable does not survive it, and rolling a new kernel across a
fleet for every batch of fixes is not feasible when a reboot cycle
takes weeks.  Mean time to exploit has gone negative: exploitation
regularly precedes the patch.  A deploy cycle built for a slow human
adversary is too slow for one that reads a fix on the list and has a
working exploit the same day; the acceptable time to mitigate a
critical bug is hours, not a day.

Three conclusions, first stated at LSF/MM/BPF, shape the design:

1. the kernel surface a fleet exposes needs massive hardening, and
   that hardening has to be deployable without a reboot;
2. mitigations have to be produced at the speed of agents, from the
   fix on the list to a signed BPF shield in the fleet;
3. BPF security has to be part of the trusted computing base, or the
   mechanism that ships the fixes becomes the next hole.

The CopyFail CVE of May 2026 is the reference case: a publicly
documented BPF LSM mitigation reached a large edge fleet in 26 to 30
hours, where the regular kernel update and reboot cycle of that fleet
was four weeks.  shirudo is built to make that the normal path, and to
make it signed, measured and agentless.

3) Design properties
--------------------

Agentless.  The BPF security layer is part of the TCB and always on,
launched from early boot.  It is signed, verified against a sealed
kernel keyring, and resilient to a malicious root user.  The BPF
control plane lives in the kernel, so every operation on it is
signature-verified, and a TPM register the TPM certifies on request
keeps the record of every operation since boot.  No daemon, no
listening socket, no open port on the target.

Packaging.  The platform itself protects only its own assets; every
piece of functionality, observability or a CVE shield, ships as a BPF
upatch.  An upatch is a signed set of related BPF programs, maps and
metadata: a light-skeleton loader plus the assets it installs.  In an
agentic age shirudo ships code, not a DSL or an API, because agents
work better with code and because a DSL is a second thing to get
right.  The agentless platform pulls upatches from a registry and
pushes telemetry to a collector; nothing ever connects in.

Agentic.  Every command has structured input and output so agents can
read and act on it: JSON status and reports, named failure
categories, verifier logs captured in full.  The intended loop is to
ingest the fix stream (lore, git trees, advisories, code audit),
classify, reproduce in a pinned kernel VM, derive a shield as a
``.bpf.c``, build and sign it, and publish it; targets pull it.  The
source tree is a set of small gadgets so an agent can hold the relevant
context at once.  The outcome is always an operator-signed upatch: the
agent proposes, the key holder signs.

4) Operator and target
----------------------

The same ``shirudo`` executable runs on both sides.  Roles are decided
by what is on disk, not by separate builds: the operator has the
private key ``signing_key.pem`` under ``/var/lib/shirudo/keys/``, the
target has the trusted set of certificates and a kernel keyring.
``shirudo status``
prints the roles it detects.  A development host may be both.

The operator holds the private signing key and runs ``genkey``,
``build`` and the ``bpm build``, ``bpm push`` and ``bpm tree append``
commands.  Those are implemented in the separate ``shirudo-build``
helper (``$(libexecdir)/shirudo/shirudo-build``), which links the CMS
signer and execs clang; the core binary only execs the helper with the
argument vector.  That exec is the single subprocess in shirudo, and it
exists only in the operator package.  The operator never opens the TPM
or the kernel keyring, and persists nothing but the keypair and the
files the caller names.

The target holds the certificate, the sealed keyring, the private bpffs
mount, the installed upatches, the eventlog and the TPM register.  It runs
``init``, ``upatch load``, ``upatch unload`` and the install side of
``bpm``.  The target never sees the private key and never signs.

Delivery is pull-based.  The operator publishes a package to an OCI
registry; the target pulls it on a timer or by hand, verifies the
signed index and the package digest, and loads the upatches inside.
shirudo owns no push transport, no fleet inventory and no rollout
coordinator.  A single ``.upatch`` copied to the target by any means
loads through the same path.

5) The signed-loader path
-------------------------

Build.  ``shirudo build fix.bpf.c -o fix.upatch`` compiles the source
with ``clang -target bpf -O2 -g``, opens the object with libbpf, calls
``bpf_object__gen_loader()`` with ``gen_hash`` set and
``bpf_object__load()`` to produce the loader instructions and data,
CMS-signs ``loader_insns || data``, and writes the ``.upatch``
container with the name, the payload SHA-256 and the attach metadata.
A pre-compiled ``.bpf.o`` is accepted as input too.  ``shirudo build --unload
<name>`` emits an unload directive instead: the same container with
flag bit 0 set, carrying the compiled ``bpf/unload.c`` template
parameterised with the target name and the expected payload digest.

Load.  ``shirudo upatch load fix.upatch`` on the target:

1. runs the pre-flight: the kernel exposes the signed-loader ABI, the
   keyring ``init`` pinned is there (the bpf keyring, or while staging
   the ``shirudo`` keyring whose serial equals the pin), the
   enforcement link is pinned, the eventlog has room, the binary's
   version identity matches ``--expect-version-id`` when given, and
   the register is the one ``init`` bound and equals ``--expect-chain``
   when given;
2. parses and bounds-checks the container;
3. loads the signed loader with ``BPF_PROG_LOAD``, naming that keyring
   as ``attr.keyring_id`` (``KEY_SPEC_BPF_KEYRING``, or the staged
   keyring's serial); the kernel verifies the CMS signature here;
4. runs the loader under ``BPF_PROG_TEST_RUN``; it creates the maps and
   loads the payload program, which the kernel checks against the
   loader's ``excl_prog_hash``;
5. attaches the payload (``BPF_LINK_CREATE`` or
   ``BPF_RAW_TRACEPOINT_OPEN``), pins the link at
   ``/run/shirudo/bpffs/upatches/<name>/link`` and every map under
   ``maps/`` beside it, and records the payload digest as the
   ``security.bpf.shirudo.payload`` xattr on the pin directory;
6. copies the artifact to ``/var/lib/shirudo/upatches/`` for
   boot-restore;
7. extends the register with ``SHA256("shirudo-upatch\0" ||
   payload_sha256 || name)`` and appends the event to the eventlog.

Unload.  ``shirudo upatch unload fix.unload.upatch`` runs the same
pre-flight and the same signature-gated ``BPF_PROG_LOAD`` of the
directive's loader, so the kernel authorises the directive exactly as
it authorises a load, and refuses a directive whose signed data does
not carry the name and expected payload its header and metadata give.
The detach itself is userspace: shirudo reads the
``security.bpf.shirudo.payload`` xattr of the live pin, compares it
constant-time against the directive's expected payload, and refuses
with ``payload_mismatch`` on disagreement or when the xattr cannot be
read.  Otherwise it extends the register with
``SHA256("shirudo-unload\0" || payload_sha256 || name)``, then unlinks
the map pins, the link pin and the pin directory and removes the
persisted ``.upatch``: an unload that fails midway leaves the upatch
attached and recorded as gone, never detached and recorded as loaded.
A missing pin is ``already_unloaded`` and extends nothing.  Load,
unload and purge all check that the register init bound this boot is
on the TPM before they change anything.  The kernel's
``bpf_sys_bpf()`` allowlist has no detach or unlink command, which is
why the detach is not inside the signed BPF; what that costs the trust
model is residual risk 1 in the threat model.

Attach kinds.  The attach metadata selects a raw tracepoint attach
(``tp_btf``, ``fentry``/``fexit``, ``lsm``), kprobe and kretprobe,
``fmod_ret``, cgroup v2 root ``cgroup_skb`` ingress and egress, IPv6
pre-routing netfilter, or ``uprobe.multi`` entry probes bound to the
target ELF's GNU build ID.  The format specification has the encoding.

6) Enforcement in the kernel
----------------------------

Two BPF objects are embedded in the binary and loaded by ``shirudo
init`` through the signed path: ``bpf/bpf2.c`` guards the ``bpf()``
syscall and the private bpffs, ``bpf/seal.c`` guards shirudo's files
and processes.  Both are BPF LSM programs.  Their verdicts compose with
SELinux, AppArmor, SMACK and Yama to the most restrictive result, and
they never override another LSM's deny.

bpf() admission.  ``lsm/bpf`` sees every ``bpf()`` command with a
``kernel`` flag that is true when the caller is a loader running in
kernel context and false for userspace.  Kernel-context calls are
allowed; they come from a loader the kernel has already verified.
Userspace ``BPF_PROG_LOAD`` is allowed only for ``BPF_PROG_TYPE_SYSCALL``
with a non-zero ``signature_size``. Userspace ``BPF_PROG_TEST_RUN`` is
restricted to the executable recorded at ``init``; kernel-context calls
from verified loaders remain allowed. This lets shirudo run loaders and
serializers while preventing root from invoking a serializer to drain
its maps. Allowed without a signature are the commands
that cannot introduce code: map create only from the executable
``init`` recorded as shirudo (signed-loader map creation runs in kernel
context and is already allowed), map update and freeze only from
shirudo's executable, object pin, link create and raw tracepoint open
(a program fd is only obtainable from a signed load or from an
already-vetted program), and the read-only commands (``*_GET_FD_BY_ID``,
``*_GET_NEXT_ID``, ``OBJ_GET_INFO_BY_FD``,
``MAP_LOOKUP_ELEM``, ``MAP_LOOKUP_BATCH``, ``MAP_GET_NEXT_KEY``,
``PROG_QUERY``, ``TASK_FD_QUERY``) that keep
``bpftool`` and ``shirudo status`` working. ``OBJ_GET`` is subject to
``lsm/bpf_map``: non-Shirudo callers can get only read-only map fds.
Everything else, including
``LINK_DETACH``, ``LINK_UPDATE``, ``PROG_ATTACH``/``PROG_DETACH``,
``BTF_LOAD`` and every map delete variant, is denied with ``-EACCES``.

``lsm/bpf_map`` denies writable map file descriptors when the caller's
executable identity is not shirudo. Root can retrieve read-only map fds
for observation, but direct map updates and writable mappings of arena
maps are denied. The ``task_prctl`` hook denies
``PR_SET_MM_EXE_FILE`` and ``PR_SET_MM_MAP`` to callers whose executable
identity is not the frozen Shirudo executable or its initrd copy. This
also denies these two operations to checkpoint and restore tools. A
process that directly executes the recorded Shirudo binary is still
identified as Shirudo; its command interface is the authorization
boundary for those operations.

``lsm/bpf_prog_load`` runs after the kernel's signature check and admits
a program only when the verdict is ``BPF_SIG_VERIFIED`` and the
signature was resolved from the keyring whose kind shirudo froze into
its identity map at init: the kernel's own bpf keyring, which the kernel
resolves itself and records without a serial, or in staging mode the
user keyring whose serial was frozen alongside.  A certificate planted
anywhere else in the caller's keyrings does not count.

bpffs and keyring guards.  The identity map (the bpffs ``s_dev``,
shirudo's executable ``(dev, ino)``, the keyring kind and serial, and
the serials of the keys the keyring holds) is written and
``BPF_MAP_FREEZE``'d before any link is created, so userspace cannot
change it for the rest of the boot. Writable map fds, map updates,
link creation, raw tracepoint opens and pins are restricted by the
same executable-identity gate.
``lsm/inode_unlink``, ``lsm/inode_rename``,
``lsm/inode_setxattr`` and ``lsm/inode_removexattr`` on shirudo's bpffs
allow the operation only when the calling task's ``mm->exe_file`` is
shirudo's binary: root ``rm`` cannot drop a pin, ``mv`` cannot replace
one (the VFS unlinks a rename's victim without ``inode_unlink``), and
nobody else can forge the payload xattr.  ``lsm/key_permission`` applies the same test
to the trust anchor in the kernel's keyrings: write, setattr and unlink
on the sealed keyring and on the keys it holds, and the unpossessed
search ``keyctl invalidate`` uses to reach a key by serial, are denied
to every task but shirudo, while viewing, listing and the possessed
search the kernel verifies signatures with stay open.  Sealing stops
keys from being added; this stops root from taking them away, so that
unlinking a key is ``shirudo keys revoke`` and nothing else.
``lsm/sb_umount``, ``lsm/move_mount``,
``lsm/sb_mount`` and ``lsm/sb_remount`` deny unconditionally, for every
caller including shirudo, any unmount, relocation, mount-over or
remount of that superblock, and ``sb_umount`` refuses any mount with
the bpffs beneath it, which a lazy unmount would take down too.  This
last set is load-bearing, not
defence in depth: shirudo is agentless, the pins are the only thing
keeping the enforcement programs alive, and one ``umount`` would
otherwise detach everything.  Every guard counts what it refuses, by
point, in a frozen map pinned beside the identity map
(``bpf/lib/shirudo_tamper.h``); ``shirudo status`` reads it back.

Filesystem seal.  ``bpf/seal.c`` relies on every inode under
``/var/lib/shirudo/`` and the installed binary carrying the xattr
``security.bpf.shirudo`` with one fixed 64-byte value, the same for
every build.  The label says what is protected, not who may touch it:
its value is public, and a binary that carries it proves nothing, since
any file system root mounts can present it.  The ``file_open`` (for
write), ``inode_unlink``, ``inode_rename``, ``inode_setattr``,
``inode_setxattr`` and ``inode_removexattr`` hooks read the label of the
target inode, both ends of a rename, and, when there is one, allow only
the task that runs the executable ``init`` recorded in the frozen
identity map, the same ``(dev, ino)`` test the bpffs guards use.
``inode_setxattr`` also lets only that task set the label itself, so
root cannot mark files of its choosing.  No ``bpf_d_path()``, no path
strings, nothing a bind mount or a mount namespace can confuse.
``bprm_check_security`` and ``bprm_committed_creds`` mark tasks that
exec a labelled binary in task-local storage, ``task_alloc`` inherits
the mark, and ``ptrace_access_check`` and ``perf_event_alloc`` deny
against marked tasks, so a root debugger cannot attach to a running
shirudo and a profiler cannot bind an event to one; a forged label can
only mark its forger.  An inode
created under a labelled directory is born with the label:
``inode_init_security`` hands it to the file system inside the
transaction that creates the inode, through
``bpf_inode_init_xattr()``, so a new file of shirudo's never exists
unlabelled.  That hook sees the parent as a bare inode and cannot
sleep to read its label, so the seal remembers a labelled directory in
inode storage from the hooks that hold a trusted handle on it:
``file_open`` of the directory, ``inode_post_setxattr`` and
``inode_post_removexattr`` on it, and the creation of a directory
under a marked parent, which marks the child in turn.  The label a new
inode gets is its parent's.  shirudo's own writers (``util/seal.c``)
open the directory before creating in it, so that it is marked and its
inode stays in memory for the duration, create relative to it, and put
the label on afterwards where the kernel could not, with no seal
attached or on a file system that takes no xattrs at creation.

Process hardening.  ``util/harden.c`` runs at startup on the target:
``PR_SET_DUMPABLE`` off, ``PR_SET_NO_NEW_PRIVS``, ``PR_SET_PTRACER`` to
nobody, ``RLIMIT_CORE`` zero, sensitive buffers locked in memory and
scrubbed after use.  The zeroing allocator in ``util/malloc.c`` wipes
freed memory; the libc allocators are poisoned project-wide.

7) Target state
---------------

``shirudo init`` is idempotent and runs on every boot from
``systemd/shirudo.service`` (``Type=oneshot``, ``KeyringMode=inherit``,
extra arguments from ``/etc/shirudo/init.env``), from the initrd in
the production configuration: after the ``enter-initrd`` phase is
measured, before the switch to the root file system, with
``/etc/shirudo`` and ``/var/lib/shirudo`` at their usual paths.
Installed in the root file system it runs before ``sysinit.target``
instead, and the target stays in staging.  It does, in order:

1. the pre-flight: root, BPF LSM active, bpffs mountable, the
   signed-loader kernel ABI, ``cert.der`` present and ML-DSA-87, the
   kernel able to parse that certificate (``CONFIG_CRYPTO_MLDSA``),
   the kernel's bpf keyring present, embedded loaders present, TPM 2.0
   reachable.  Every
   check is hard; all failures are reported together as
   ``init_prereqs_missing`` and nothing is touched.  ``shirudo init
   --check-only`` stops here.  In the initrd, told by
   ``/etc/initrd-release``, ``init`` also binds the root's
   ``/var/lib/shirudo`` read-only at its usual path and reads the
   trusted set from the initrd's own ``/etc/shirudo/keys``;
2. mounts the private bpffs at ``/run/shirudo/bpffs`` with
   ``mode=0700,nosuid,nodev,noexec``;
3. removes state left behind by features that no longer exist;
4. enrols the trusted set in the kernel's bpf keyring and seals it
   with ``KEYCTL_RESTRICT_KEYRING`` so nothing can be linked into it
   for the rest of the boot.  The set is ``cert.der`` plus every
   ``trusted/<fingerprint>.der`` with a vouch beside it that verifies
   under the primary or under a member admitted before it, less the
   fingerprints the ``revoked/`` directory names (the `key-lifecycle
   <key-lifecycle.rst>`__ guide).  A keyring found sealed is reused
   when it holds exactly that set, which ``init`` tells by the
   descriptions the kernel gives the certificates, and refused when it
   holds anything else.  That needs the kernel booted with
   ``bpf.keyring_unsealed=1`` and ``init`` run from the initrd.  A
   kernel that sealed the bpf keyring empty at boot makes ``init``
   stage the primary certificate alone instead: a ``shirudo`` keyring
   in the user keyring, sealed with ``KEYCTL_SETPERM`` to view, read
   and search only, until the next reboot;
5. labels ``/var/lib/shirudo/`` with ``security.bpf.shirudo`` and
   appends the record an initrd run left under ``/run`` to the
   eventlog; the initrd run itself skips both, its root being
   read-only;
6. loads bpf2 and, unless ``--no-seal``, seal through the signed path,
   freezes and pins the identity map (the bpffs, the executable that
   keeps running the target, from the initrd also the initrd's own
   copy for that run, the keyring kind and serial, and the serials of
   the keys it holds), creates the links and pins each one before
   doing anything else fallible;
7. re-applies every ``.upatch`` under ``/var/lib/shirudo/upatches/`` in
   sorted name order, all or nothing;
8. binds this boot's measurement register and extends it once with
   ``SHA256("shirudo-init\0" || cert_sha256 || set_digest ||
   tree_root)``, where ``cert_sha256`` covers the enrolled
   certificates (one digest, or the SHA-256 over the sorted digests of
   several), ``set_digest`` is the SHA-256 of the sorted listing of the
   restored set and ``tree_root`` the upatch tree's projection root
   (zeros without a tree), and appends the event.

Boot-restore extends the register by exactly one event however many
upatches it restores.  The register starts from zero at every boot, so
an operator predicts its value from the certificate and the installed
set alone (``shirudo attest predict``); no history is needed.  If any
re-apply fails the register is not written and ``status`` reports
``degraded``.  A re-run of ``init`` finds the register bound and on
record and leaves it alone; one that finds the recorded register gone
refuses ``tampered`` until the next TPM reset.

Measurement register.  The measurement lives in a TPM 2.0 NV index
(default ``0x01818E00``) built the way systemd builds its NvPCRs: an
extend-only index (``TPM2_NT_EXTEND``) whose contents clear at every
TPM reset (``TPMA_NV_CLEAR_STCLEAR``) and whose write policy is
``PolicyOR(PolicyNvWritten(YES), PolicyNvWritten(NO) || PolicyPCR(PCRs
9, 11))``, computed from the values PCRs 9 and 11 hold when ``init``
binds the register.  ``init`` runs from the initrd, after systemd has
measured ``enter-initrd`` into PCR 11 and before ``leave-initrd``
moves it, performs the first write through the PCR branch and then
extends PCR 9 with the record ``nvpcr-init:shirudo:0x1818e00:<name>``
(systemd's ``nvpcr-init`` format, ``<name>`` being the index's TPM
name), so that branch can never be satisfied again until the next
reset and nothing that runs after the initrd can bind at all; every
later extend presents the written branch.  An index undefined and
recreated at runtime therefore stays unwritable, and one recreated
under a weaker policy has a name other than the one ``init`` recorded
and anchored.  The record carries both PCR values and whether the
initrd was running, so a verifier pins the ``enter-initrd`` value and
refuses a binding made from the root file system.
Reads need no authorisation; defining and undefining the index needs
the owner hierarchy, whose password, when set, comes from
``tpm.owner_auth`` in ``/etc/shirudo/shirudo.conf``.  Every
state-changing command reads the register first and refuses with
``tampered`` when ``--expect-chain`` disagrees or the index is not the
one ``init`` recorded.  There is no TPM opt-out; an unmeasured target
is indistinguishable from a tampered one.

Eventlog.  ``/var/lib/shirudo/eventlog`` (mode 0600) holds one JSON
line per register extension: timestamp, boot ID, type (``init``,
``upatch_load``, ``upatch_unload``, ``tree_op``), the digest extended,
and the name and payload digest, the set digest or the tree operation.
The ``init`` record also carries the binding: the PCR value the policy
was computed from, the index name, the anchor record with its digest,
and the TPM's reset count, which tells one register period from the
next.  Replaying this boot's records from its ``init`` on must
reproduce the live value; ``shirudo status`` does that replay, checks
that the live index carries the recorded name, and reports ``Chain vs
eventlog`` and ``Anchored``.  When ``eventlog.max_bytes`` would be
exceeded, the operation refuses with ``eventlog_full`` before any load
or extend, so register and log never diverge.

Attestation.  ``shirudo attest --nonce=<hex>`` emits a JSON evidence
document: a ``TPM2_Quote`` over the SHA-256 bank (PCRs 0-7, 9 and
11-15 by default) and a ``TPM2_NV_Certify`` of the register, both
signed by the attestation key and carrying the nonce, the key's public
area and name, the PCR values, this boot's eventlog records, the
endorsement key certificate when the TPM holds one, and the firmware
and systemd measurement logs.  The attestation key is a restricted
P-256 ECDSA primary under the endorsement hierarchy with a fixed
template, so the same TPM always yields the same key; an operator
records its name once when enrolling the target.  ``shirudo attest
challenge`` makes a credential under the target's endorsement key for
that name, ``attest --challenge`` activates it in the TPM while
attesting, and ``verify --expect-credential`` checks the recovered
value, so the key is shown to sit in the TPM the endorsement
certificate describes instead of being taken on trust.  ``shirudo
attest verify`` on the operator checks the signatures and the nonce,
that the
quote covers the listed PCRs, that the certified index has the public
area a register bound to the recorded PCR value must have, that the
records replay to the certified value, that the anchoring PCR carries
the anchor, and that the register equals the value ``shirudo attest
predict`` computes from the certificate, the installed artifacts and
the tree root, or an ``--expect-chain`` the operator computed from
those plus the events since boot.  ``attest`` touches only the
target's TPM; ``verify`` and ``predict`` touch no TPM at all.

Files.  Under ``/var/lib/shirudo/``: ``keys/cert.der`` (and
``keys/signing_key.pem`` on an operator), ``keys/trusted/`` (the
further certificates with their vouches), ``keys/revoked/``,
``eventlog``, ``upatches/`` (installed artifacts), ``incoming/``
(staging), ``locks/`` and ``bpm/`` (registry indexes, packages, tree
state).  Under ``/run/shirudo/``, per boot: the ``bpffs/`` mount with
``lsm_link``, the ``bpf2_*_link`` and ``seal_*_link`` pins, the frozen
``identity`` map and ``upatches/<name>/``, and ``eventlog.pending``
between the initrd run and the root's; it lives under ``/run``
because that is what
systemd carries from the initrd into the root file system, so pins
made before the switch keep their links.  Under
``/etc/shirudo/``: ``shirudo.conf``, ``init.env``, ``map-export.env``,
``node.labels`` and ``bpm/`` (``registries.d/``, ``keys/``,
``upatch-tree.conf``, ``environment``).  ``shirudo config`` prints the
effective configuration with a comment on every key.

8) Packages and registries
--------------------------

A BPM package (``.bee``) is a gzip tarball with the ``Beefile``, the
built ``upatches/*.upatch`` and their unload directives, a
``README.md``, the signing ``cert.der`` and a ``build-environment.json``.
``shirudo bpm build <dir> --version <v>`` builds and signs every
``[[upatches]]`` entry through ``shirudo-build``.  ``shirudo bpm push
<pkg.bee> oci://host/ns/name`` uploads it as an OCI artifact
(``application/vnd.shirudo.bpm.package.v1+gzip``) with the certificate
as a referrer and, when given the signing material, adds the version to
the registry's detached-CMS-signed index at
``shirudo/bpm-index:stable``.  Published versions are immutable; an
index that already lists a version with other digests is refused.

On the target, ``shirudo bpm config register add <name> oci://host
--key-file cert.der`` records the registry and the certificate that
must sign its index.  ``shirudo bpm repo update`` fetches and verifies
the index; ``shirudo bpm install <name>/<pkg>[@ver]`` (or an ``oci://``
reference) pulls, verifies, unpacks and loads; ``upgrade`` moves
installed packages to the newest indexed version; ``uninstall`` loads
the package's unload directives; ``list`` and ``info`` inspect.
``shirudo bpm key`` manages the active certificate and refuses to switch
to a different one while a key is active.  The ``repo update`` and
``tree sync`` timers (60 s) and the map-export and keepalive timers
(5 s) are the only always-on infrastructure.

upatch trees.  A tree is an append-only, globally ordered sequence of
``add`` and ``delete`` operations published as a CMS-signed JSON
document (``application/vnd.shirudo.upatch.tree.v2+json``), each
``.upatch`` pushed as an immutable OCI manifest.  Every operation
carries a selector (architecture, kernel release prefix, kernel build
ID, Kconfig values, node labels) that ``shirudo bpm tree sync``
evaluates locally against ``uname``, ``/sys/kernel/notes``,
``/proc/config.gz`` and ``/etc/shirudo/node.labels``; matching
operations apply in sequence order, each applied one is measured into
the register as a ``tree_op`` event (``SHA256("shirudo-tree\0" || seq
|| operation_digest)``), and the node's projection root enters the next
boot's ``init`` event.  ``shirudo bpm tree append <pkg.bee>
oci://host/repo [--op add|delete]`` publishes from the operator.  The
tree is enabled by ``/etc/shirudo/bpm/upatch-tree.conf`` and its timer;
without that file nothing changes.  The publication format is in the
format specification's companion section below.

Registry access honours ``BPM_OCI_SCHEME``, ``BPM_OCI_CA_FILE``,
``BPM_OCI_USERNAME``/``BPM_OCI_PASSWORD``, ``REGISTRY_AUTH_FILE`` and
``DOCKER_CONFIG``.  Every libcurl client in shirudo speaks TLS 1.3 with
a hybrid ML-KEM key exchange only (X25519MLKEM768, SecP256r1MLKEM768);
there is no classical fallback.  The registry is untrusted: it can
withhold or replay a signed publication, it cannot forge one.

Tree publication format.  The ``stable`` manifest has two layers, the
publication and its detached CMS signature.  The publication is::

    {"schema": 2, "tree_id": "...", "generation": N,
     "parent_manifest_digest": "sha256:...",
     "base": {"seq": 0}, "operations": [...], "head": {"seq": N}}

and each operation is::

    {"seq": N, "op": "add" | "delete", "id": "...",
     "selector": {...},
     "artifact": {"repository": "...", "manifest_digest": "sha256:...",
                  "layer_digest": "sha256:...", "payload_sha256": "..."},
     "operation_digest": "..."}

where ``operation_digest`` is the SHA-256 of the compact JSON of the
same object without that field, with selector keys and list values
sorted.  ``tree append`` fetches and verifies the current publication
(a missing one starts generation 1 with the package name as tree id),
pushes each artifact as a manifest tagged ``upatch-<id>-<payload16>``,
appends one operation per entry with ``seq = head + 1``, and
republishes with ``generation + 1`` and ``parent_manifest_digest`` set
to the manifest it replaced.  A publication with a number outside the
signed 64-bit range, or a ``generation`` or ``head`` at its top that
leaves no successor, is refused.  A ``delete`` publishes the entry's
unload directive and is accepted by a target only for an id it loaded
from the same tree.

9) Observability
----------------

``shirudo status`` reports the machine it runs on: roles, version ID,
the conditions ``LsmAttached``, ``KeyringSealed``, ``ChainIntact`` and
``TpmMeasured`` with an ``OK``, ``WARN`` or ``ALERT`` verdict each, the
keyring serial against its pin, the register against this boot's
eventlog replay and its anchor, the on-disk assets, and with
``--include-system``, ``--include-eventlog``, ``--include-kernellog``
and ``--include-modules`` the corresponding detail.  The register is
always read: a status that did not ask the TPM would be a status the
target wrote about itself.  The overall
``status`` is ``ok``, ``degraded``, ``init-pending``, ``lsm-off`` or
``tampered``.  ``--json`` emits the same as one document; ``--otel``
pushes it as a keepalive log record.  ``status`` is the target's own
account of itself; ``shirudo attest`` (section 7) is the account the
TPM signs.

``shirudo upatch list``, ``info``, ``get`` and ``map`` inspect
artifacts and loaded state.  ``info`` describes the container offline,
signed decoders included, and is advisory; ``get`` reads the loaded
program's ``line_info`` and BTF from the kernel and is authoritative.
``upatch map`` reads pinned maps, runs the upatch's signed Lua decoder,
and prints, appends NDJSON, or exports over OTLP.  The export path, its
decoders and the collector integration are described in
`telemetry <telemetry.rst>`__.

Every command logs through ``syslog(3)`` as ``shirudo`` to
``LOG_AUTHPRIV``; ``journalctl -t shirudo`` shows it.

10) Failure reporting
---------------------

``upatch load`` and ``upatch unload`` take ``--report=<path>`` and write
one JSON document: ``result``, the ``phase`` reached (``pre_flight``,
``parse``, ``signed_loader_load``, ``payload_load``, ``link_create``,
``pin``, ``persist``, ``tpm_extend``, ``done``), ``errno`` and its
name, a ``category``, a message, the verifier log when the verifier
spoke, the loader's return value, the artifact's path and name, the
kernel release, and the NV index and chain value after the operation.

The categories are ``ok``, ``tampered``, ``keyring_missing``,
``lsm_denied``, ``signature_rejected``, ``signature_unsupported``,
``verifier_rejected``, ``parser_rejected``, ``btf_mismatch``,
``payload_mismatch``, ``already_unloaded``, ``detach_failed``,
``tpm_error``, ``eventlog_full``, ``kernel_abi_unsupported``,
``init_prereqs_missing``, ``version_mismatch`` and ``unknown``.
Automation treats ``tampered`` as "refresh state, then decide", never
as "retry the same input": a concurrent legitimate operator produces
it too.

11) Runtime design
------------------

The core binary never forks or execs; the one exception is the
operator-only ``shirudo build`` dispatch described above.  Everything
else is a library call or a syscall: libbpf for BPF, raw ``keyctl``
for keyrings, tpm2-tss for the TPM, libcrypto for digests and
certificate parsing, libcurl over libssl for registries and OTLP,
libelf and zlib for objects, LuaJIT for decoders.  The in-tree
``util/json.c`` is the only JSON code and ``util/parse-options.c`` the
only option parser.  Nothing else is linked; every additional library
is attack surface.

Both profiles need OpenSSL 3.5 or newer for ML-DSA.  The operator links
the system shared libraries.  The target image (``make target``) links
a static OpenSSL, an OpenSSL-backed static libcurl and a static tpm2-tss
that ``make target-deps`` builds from source, plus static libbpf,
libelf, zlib, zstd and LuaJIT, so it runs on a
distribution whose OpenSSL predates ML-DSA.  ``SHIRUDO_VERSION_ID``
hashes the source tree and build configuration, not binary bytes, so
the same source yields the same identity on x86-64, arm64 and riscv64;
the pre-flight refuses a ``version_mismatch``.

shirudo requires Linux v7.4 or newer and the current upstream clang.
There are no fallbacks for older kernels: a missing feature
fails the build or the pre-flight with a message, never a degraded
mode.

12) Project layout
------------------

::

    shirudo/
        shirudo.c               command dispatch table
        builtin-*.c             one file per top-level command
        util/                   shared userspace library
        bpf/                    bpf2.c, seal.c, unload.c, loaders

        tools/shirudo-build/    operator-only helper: compile, sign,
                                bpm build and publish, tree append

                                installer
        tools/gen-vmlinux-h/    vmlinux.h generator

``shirudo help --list-cmds`` prints the supported command set.

13) Kernel work this design waits for
-------------------------------------

Several residual risks in the threat model are closed by kernel work in
flight rather than by shirudo code:

- the signed loader creating the link and pinning it, and detaching
  and unloading in kernel, so the whole lifecycle is signature-covered
  (residual risk 1);
- BPF in-kernel sockets, so keepalive, status and alerting can be sent
  from kernel context without a userspace timer;
- xattr getters for kernfs, so ``security.bpf.*`` labels can be
  enforced on cgroups;
- ``fmod_ret`` coverage of the whole kernel build, so a shield can
  reject a call at any function rather than at the instrumented ones;
- signed-loader support for every program type, including struct_ops.

shirudo tracks the current upstream kernel; when one of these lands,
the corresponding shirudo change follows and the residual is removed
from the threat model.
