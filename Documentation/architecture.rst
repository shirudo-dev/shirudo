shirudo architecture
====================

This document describes the implemented design: what runs where, which
kernel mechanisms carry the enforcement, what state a target holds, and
how artifacts, packages and telemetry move.  The code is authoritative;
when this document and the code disagree, the code is right and this
document has a bug.  The security argument behind the design is in
`threat-model <threat-model.rst>`__, the byte-level artifact format in
`upatch-spec <upatch-spec.rst>`__, and the export path in
`telemetry <telemetry.rst>`__.

1) What shirudo is
------------------

shirudo is a BPF security platform.  It ships BPF live patches
("upatches") to Linux targets, and it makes sure a target runs only the
BPF its operator signed.  Both halves are needed: a patching mechanism
any root process can use is an attack surface, and an enforcement
mechanism without a way to ship fixes is a wall nobody can work behind.

Once ``shirudo init`` has run, the kernel accepts BPF programs from
userspace only through signed loader programs.  A loader is a
``BPF_PROG_TYPE_SYSCALL`` program generated by libbpf's gen_loader on
the operator; it embeds the ``bpf()`` calls that create the maps and
load the payload program.  The operator CMS-signs the loader
instructions and data with an ML-DSA-87 key.  The target kernel
verifies that signature at ``BPF_PROG_LOAD`` against the certificate in
the sealed bpf keyring, before the verifier and before any LSM hook
runs.  The payload program is hash-locked to the loader
(``excl_prog_hash``), so a signature over a few kilobytes of loader
covers every instruction that ends up attached.

The kernel-side enforcement is a set of embedded BPF LSM programs loaded
during trusted bootstrap, before the signature-admission gates attach.
Authenticated initrd boot protects that bootstrap; subsequent upatch loads
use the signed-loader path above. Every upatch state change extends a
per-boot TPM measurement register
anchored in a PCR, so an operator predicts from the signed set what a
target must report and has the TPM certify that it does.
The userspace side is one binary with git-like subcommands; on the
target there is no daemon and no socket, only one-shot invocations
driven by systemd timers.

2) Why shirudo exists
---------------------

The kernel's CVE stream runs at dozens of fixes a day, and that churn
is not going to end.  The distribution model of enabling every Kconfig
option for compatibility and then carrying a kernel that deviates from
upstream stable does not survive it, and rolling a new kernel across a
fleet for every batch of fixes is not feasible when a reboot cycle
takes weeks.  Mean time to exploit has gone negative: exploitation
regularly precedes the patch.  A deploy cycle built for a slow human
adversary is too slow for one that reads a fix on the list and has a
working exploit the same day; the acceptable time to mitigate a
critical bug is hours, not a day.

Three conclusions, first stated at LSF/MM/BPF, shape the design:

1. the kernel surface a fleet exposes needs massive hardening, and
   that hardening has to be deployable without a reboot;
2. mitigations have to be produced at the speed of agents, from the
   fix on the list to a signed BPF shield in the fleet;
3. BPF security has to be part of the trusted computing base, or the
   mechanism that ships the fixes becomes the next hole.

The CopyFail CVE of May 2026 is the reference case: a publicly
documented BPF LSM mitigation reached a large edge fleet in 26 to 30
hours, where the regular kernel update and reboot cycle of that fleet
was four weeks.  shirudo is built to make that the normal path, and to
make it signed, measured and agentless.

3) Design properties
--------------------

Agentless.  The BPF security layer is part of the TCB and always on,
launched from early boot.  It is signed, verified against a sealed
kernel keyring, and resilient to a malicious root user.  The BPF
control plane lives in the kernel, so every operation on it is
signature-verified, and a TPM register the TPM certifies on request
keeps the record of every operation since boot.  No daemon, no
listening socket, no open port on the target.

Packaging.  The platform itself protects only its own assets; every
piece of functionality, observability or a CVE shield, ships as a BPF
upatch.  An upatch is a signed set of related BPF programs, maps and
metadata: a light-skeleton loader plus the assets it installs.  In an
agentic age shirudo ships code, not a DSL or an API, because agents
work better with code and because a DSL is a second thing to get
right.  The agentless platform pulls upatches from a registry and
pushes telemetry to a collector; nothing ever connects in.

Agentic.  Every command has structured input and output so agents can
read and act on it: JSON status and reports, named failure
categories, verifier logs captured in full.  The intended loop is to
ingest the fix stream (lore, git trees, advisories, code audit),
classify, reproduce in a pinned kernel VM, derive a shield as a
``.bpf.c``, build and sign it, and publish it; targets pull it.  The
source tree is a set of small gadgets so an agent can hold the relevant
context at once.  The outcome is always an operator-signed upatch: the
agent proposes, the key holder signs.

4) Operator and target
----------------------

The same ``shirudo`` executable runs on both sides.  Roles are decided
by what is on disk, not by separate builds: the operator has the
private key ``signing_key.pem`` under ``/var/lib/shirudo/keys/``, the
target has the trusted set of certificates and a kernel keyring.
``shirudo status``
prints the roles it detects.  A development host may be both.

The operator holds the private signing key and runs ``genkey``,
``build`` and the ``bpm build``, ``bpm push`` and ``bpm tree append``
commands.  Those are implemented in the separate ``shirudo-build``
helper (``$(libexecdir)/shirudo/shirudo-build``), which links the CMS
signer and executes clang. Image building and offline ``image verify`` also
dispatch to this helper; it runs the standard ``veritysetup`` executable
for formatting and verification. These subprocesses belong to operator
operations. Target commands use linked libraries and kernel APIs. The
operator never opens the TPM or the kernel keyring, and persists nothing
but the keypair and the files the caller names.

The core binary exposes the operator-only BPM commands only when it can
resolve ``shirudo-build``.  The installed operator package provides the
helper; a checkout must set ``SHIRUDO_BUILD`` or put both the checkout
root and ``tools/shirudo-build`` on ``PATH``.  Without the helper,
``shirudo bpm --help`` shows the target command set and rejects ``build``.

The target holds the certificate, the sealed keyring, the private bpffs
mount, the installed upatches, the eventlog and the TPM register.  It runs
``init``, ``upatch load``, ``upatch unload`` and the install side of
``bpm``.  The target never sees the operator's private key.  Its separate
boot-scoped RSA key authorizes only local TPM register extensions.

Delivery is pull-based.  The operator publishes a package to an OCI
registry; the target pulls it on a timer or by hand, verifies the
signed index and the package digest, and loads the upatches inside.
shirudo owns no push transport, no fleet inventory and no rollout
coordinator.  A single ``.upatch`` copied to the target by any means
loads through the same path.

5) The signed-loader path
-------------------------

Build.  ``shirudo build fix.bpf.c -o fix.upatch`` compiles the source
with ``clang -target bpf -O2 -g``, opens the object with libbpf, calls
``bpf_object__gen_loader()`` with ``gen_hash`` set and
``bpf_object__load()`` to produce the loader instructions and data,
appends the name, the attach metadata and the decoders to the data as
signed sections, CMS-signs ``loader_insns || data``, and writes the
``.upatch`` container with the name and the payload SHA-256 in its
header.
A pre-compiled ``.bpf.o`` is accepted as input too.  ``shirudo build --unload
<name>`` emits an unload directive instead: the same container with
flag bit 0 set, carrying the compiled ``bpf/unload.c`` template
parameterised with the target name and the expected payload digest.

Load.  ``shirudo upatch load fix.upatch`` on the target:

1. runs the pre-flight: the kernel exposes the signed-loader ABI, the
   kernel BPF keyring matches the serial ``init`` froze, the
   enforcement link is pinned, the eventlog has room, the binary's
   version identity matches ``--expect-version-id`` when given, and
   the register is the one ``init`` bound and equals ``--expect-chain``
   when given;
2. parses and bounds-checks the container;
3. loads the signed loader with ``BPF_PROG_LOAD``, naming that keyring
   as ``attr.keyring_id`` (``KEY_SPEC_BPF_KEYRING``); the kernel verifies the CMS signature here;
4. runs the loader under ``BPF_PROG_TEST_RUN``; it creates the maps and
   loads the payload program, which the kernel checks against the
   loader's ``excl_prog_hash``;
5. attaches the payload (``BPF_LINK_CREATE`` or
   ``BPF_RAW_TRACEPOINT_OPEN``), checks that the link the kernel
   reports is at the site the metadata names (the root cgroup of the
   initial cgroup namespace, the initial network namespace, the kprobe
   symbol and offset, the uprobe offsets) and refuses
   ``attach_scope_mismatch`` otherwise, pins the link at
   ``/run/shirudo/bpffs/upatches/<name>/link`` and every map under
   ``maps/`` beside it, and records the payload digest as the
   ``security.bpf.shirudo.payload`` xattr on the pin directory;
6. copies the artifact to ``/var/lib/shirudo/upatches/`` for
   boot-restore;
7. extends the register with ``SHA256("shirudo-upatch\0" ||
   payload_sha256 || name)`` and appends the event to the eventlog; an
   archive copy that fails, or a register that refuses the event, undoes
   the load, pins and archive.

Unload.  ``shirudo upatch unload fix.unload.upatch`` runs the same
pre-flight and the same signature-gated ``BPF_PROG_LOAD`` of the
directive's loader, so the kernel authorises the directive exactly as
it authorises a load.  The detach itself is userspace: shirudo reads the
``security.bpf.shirudo.payload`` xattr of the live pin, compares it
constant-time against the directive's expected payload, and refuses
with ``payload_mismatch`` on disagreement or when the xattr cannot be
read.  Otherwise it extends the register with
``SHA256("shirudo-unload\0" || payload_sha256 || name)`` and only then
unlinks the map pins, the link pin and the pin directory and removes
the persisted ``.upatch``: a process stopped between the two leaves a
register that says more than happened, never a detach it does not
know.  A missing pin is ``already_unloaded`` and extends nothing.  The kernel's
``bpf_sys_bpf()`` allowlist has no detach or unlink command, which is
why the detach is not inside the signed BPF; the target name and the
expected payload are signed sections of the directive, so what that
costs the trust model is the moment of the detach alone, residual risk
1 in the threat model.

Attach kinds.  The attach metadata selects a raw tracepoint attach
(``tp_btf``, ``fentry``/``fexit``, ``lsm``), kprobe and kretprobe,
``fmod_ret``, cgroup v2 root ``cgroup_skb`` ingress and egress, IPv6
pre-routing netfilter, or ``uprobe.multi`` entry probes bound to the
target ELF's GNU build ID.  The format specification has the encoding.

6) Enforcement in the kernel
----------------------------

The target requires an authenticated runtime image and a signed config image.
The runtime is mounted at ``/run/shirudo/runtime`` and the config at
``/run/shirudo/config`` with ``noexec``. Neither replaces the host root.
Every runtime executable is eligible for task authority after successful exec.

The binary embeds ``bpf/bpf2.c`` for admission, device and mount protection,
and ``bpf/seal.c`` for writable-state labels and process protection.
``bpf/admission.h`` and ``bpf/seal.h`` contain the checks shared by their
programs; ``bpf/verity_policy.h`` supplies runtime-device and task lookups.
Initialization always loads this pair and all its hooks. There is no mode
selector, executable inode identity or user-keyring staging path.

These are bootstrap objects, not signed upatch-loader artifacts. In the
production boot flow their provenance comes from the authenticated initrd.
The map-access, ``bpf_prog_load`` and ``bpf`` gates attach last, after the
selected objects have loaded and their identity maps are frozen. Subsequent
upatch code must enter through the signature-gated loader path.
Both objects contain BPF LSM programs.  Their verdicts compose with
SELinux, AppArmor, SMACK and Yama to the most restrictive result, and
they never override another LSM's deny.

bpf() admission.  ``lsm/bpf`` sees every ``bpf()`` command with a
``kernel`` flag that is true when the caller is a loader running in
kernel context and false for userspace.  Kernel-context calls are
allowed; they come from a loader the kernel has already verified.
Userspace ``BPF_PROG_LOAD`` is allowed only for ``BPF_PROG_TYPE_SYSCALL``
with a non-zero ``signature_size``. Userspace ``BPF_PROG_TEST_RUN`` is
restricted to tasks authorized by successful exec from the runtime image;
kernel-context calls from verified loaders remain allowed. This lets Shirudo
run loaders and serializers while preventing root from invoking a serializer
to drain its maps. Map creation, update and freeze, object pin, link creation
and raw tracepoint open also require that task authority, and so does
``PERF_EVENT_IOC_SET_BPF``, the perf event ioctl that attaches a program
without a ``bpf()`` command, which ``lsm/file_ioctl`` and
``lsm/file_ioctl_compat`` deny to every other caller.
The read-only commands (``*_GET_FD_BY_ID``,
``*_GET_NEXT_ID``, ``OBJ_GET_INFO_BY_FD``,
``MAP_LOOKUP_ELEM``, ``MAP_LOOKUP_BATCH``, ``MAP_GET_NEXT_KEY``,
``PROG_QUERY``, ``TASK_FD_QUERY``) keep
``bpftool`` and ``shirudo status`` working. ``OBJ_GET`` is subject to
``lsm/bpf_map``: non-Shirudo callers can get only read-only map fds.
Everything else, including
``LINK_DETACH``, ``LINK_UPDATE``, ``PROG_ATTACH``/``PROG_DETACH``,
``BTF_LOAD`` and every map delete variant, is denied with ``-EACCES``.

``lsm/bpf_map`` denies writable map descriptors to tasks without authority.
Root can retrieve read-only map descriptors for observation, but direct map
updates and writable arena mappings require an authorized task. Device records
are private because they contain kernel pointers. ``task_prctl`` denies
``PR_SET_MM_EXE_FILE`` and ``PR_SET_MM_MAP`` to untrusted tasks. Rewriting
``mm->exe_file`` never creates task authority.

``lsm/bprm_check_security`` keeps that boundary from being stepped
around through the environment: every exec from the runtime image runs in secure-exec mode (``AT_SECURE``), as a
set-user-ID program does.  The dynamic loader then ignores
``LD_PRELOAD``, ``LD_AUDIT``, ``LD_LIBRARY_PATH`` and the other
variables glibc treats as unsafe, and libraries ignore what they read
with ``secure_getenv()``, among them OpenSSL's ``OPENSSL_CONF`` and
``OPENSSL_MODULES``.  The same hook refuses the exec, counted as
``ExecTraced``, when the task is traced (``LSM_UNSAFE_PTRACE``): a
tracer that carries over into the new image, set up with
``PTRACE_TRACEME`` or attached to the parent, would own it, and the
seal's ptrace guard only stops a tracer attaching later.  ``strace``
and ``gdb`` therefore cannot start shirudo on a target.  The hook runs
on every binary handler pass, so a script that names shirudo as its
interpreter gets the same.

``lsm/bpf_prog_load`` runs after the kernel's signature check and admits
a program only when the verdict is ``BPF_SIG_VERIFIED`` and the signature
was resolved from the kernel's BPF keyring. The kernel normally records no
serial for this singleton; a nonzero serial must match the frozen record.
A certificate in another caller keyring cannot authorize a load.

Image content by descriptor. Everything a command takes from the
runtime or config image, the bootstrap settings, the configuration,
the certificate, the key set, the registries, the tree configuration
and the node labels, is opened from the verified root descriptor with
``openat2`` under ``RESOLVE_BENEATH``, never through a path string;
``/proc/self/fd`` names in particular are not used for them.
bpffs and keyring guards. The identity map contains the bpffs and run-device
numbers, runtime root hash, BPF keyring kind and serial, enrolled key
serials, the selected NV index, the NV writer's public modulus and
nonsecret input, and the name of the TPM's attestation key, which
every later TPM handle is compared against.
It is written and frozen before the admission gates attach.
The task map is seeded with the authenticated bootstrap task, then frozen
against userspace writes. Runtime exec and fork hooks maintain its marks.
Expected config roots remain writable only by trusted tasks preparing a
mapping. Other device records are maintained by the kernel hooks.
``lsm/inode_unlink``, ``lsm/inode_rename``,
``lsm/inode_setxattr`` and ``lsm/inode_removexattr`` on shirudo's bpffs
allow the operation only for a task with runtime authority: root ``rm`` cannot drop a pin, ``mv`` cannot replace
one (the VFS unlinks a rename's victim without ``inode_unlink``), and
nobody else can forge the payload xattr. ``lsm/inode_mkdir``,
``lsm/inode_symlink`` and ``lsm/inode_link`` there are shirudo's too,
so that no symbolic link of root's stands where a load would make its
pin directory and no hard link of root's keeps a pin past its unlink.  ``lsm/key_permission`` applies the same test
to the trust anchors in the kernel's keyrings: write, setattr and unlink
on the sealed bpf and dm-verity keyrings and on the keys they hold, and the unpossessed
search ``keyctl invalidate`` uses to reach a key by serial, are denied
to every task but shirudo, while viewing, listing and the possessed
search the kernel verifies signatures with stay open.  Sealing stops
keys from being added; this stops root from taking them away, so that
signer removal happens through signed config activation.
``lsm/kernel_load_data`` and ``lsm/kernel_read_file`` refuse a kexec
image or initramfs to every task, since a kexec would carry this boot's
TPM state under a kernel of root's choosing.
``lsm/sb_umount``, ``lsm/move_mount``,
``lsm/sb_mount`` and ``lsm/sb_remount`` deny unconditionally, for every
caller including shirudo, direct unmount, relocation, mount-over and
remount of that superblock. ``lsm/sb_umount`` also walks what an unmount
would take down, the subtree of the mount and what propagation carries to
its peers and slaves, and refuses one that reaches the bpffs mount init
recorded when it opened the bpffs root with the guards live; a copy in
another mount namespace is any process's to drop. See residual risk 3 in
the threat model.
The pins are the only thing
keeping the enforcement programs alive, and one ``umount`` would
otherwise detach everything. Named refusal points increment counters in
a frozen map pinned beside the identity map
(``bpf/lib/shirudo_tamper.h``); ``shirudo status`` reads it back. Device, parent-mount and process checks do not yet have counters. A refusal
at an earlier image check therefore need not increment a shared counter.
Search denials on NV keys are not counted: traversal probes use the
same permission as signing and invalidation.

Filesystem seal. Initialization labels existing state under
``/var/lib/shirudo/`` with ``security.bpf.shirudo``. The fixed 64-byte label
marks a protected target; its public value does not authorize a caller.
The ``file_open`` (for write), ``inode_unlink``, ``inode_rename``,
``inode_setattr``, ``inode_setxattr`` and ``inode_removexattr`` hooks require
the caller's committed task authority, and so do ``inode_create``,
``inode_mkdir``, ``inode_symlink``, ``inode_mknod``, ``inode_link`` and a
rename into a marked directory: a sealed directory takes new entries from
shirudo alone. ``inode_copy_up`` refuses the overlay copy-up of a marked
inode, so a write through an overlay mounted over sealed state fails
rather than landing, label and all, in the upper directory. Runtime and
config files use dm-verity and receive no seal writes.
Only an authorized caller may set the exact seal xattr, including on an
unlabelled inode. A binary carrying a copied label gains no authority.
A path the caller names for shirudo to write (``--report``, ``--out``,
``--json``, a ``bpm pull``) is opened by ``seal_output_open()``: a
regular file without a label, not created under a labelled directory,
not reached through a symbolic link, so root cannot point the authority
at sealed state.

A label of any size, or an error reading it, requires caller authority,
except for ``ENODATA``, ``EOPNOTSUPP``, ``EACCES`` and ``EPERM``. The latter
two exceptions preserve write-only opens and unlinking unreadable files:
the xattr kfunc checks the caller's read permission. Failure to allocate
scratch storage also requires caller authority. Rename checks both the
source and an existing destination. ``inode_setattr``
covers truncate, chmod, chown and timestamp changes to labelled targets.

``inode_init_security`` uses ``bpf_inode_init_xattr()`` to give a new inode
its parent's label inside the filesystem's creation transaction. That hook
cannot sleep to read the parent xattr, so it uses an inode-storage directory
mark populated by directory opens, post-xattr hooks and directory creation
under a marked parent. Shirudo's writers hold an open parent directory and
create files relative to it; they also apply the label after creation when
the kernel could not. Cached marks can be absent after inode eviction, when
a creation, link or rename can introduce an unlabelled inode; shirudo opens
sealed state without following symbolic links, refuses an entry under a
labelled directory that lacks the label, and ``init`` ignores such an entry
instead of labelling it. Existing writable descriptors and mappings are not
revoked.

``ptrace_access_check`` and ``perf_event_alloc`` deny against tasks already
marked when those hooks run. The perf allocation check is not serialized with
exec; the separate `perf/exec race investigation
<https://github.com/shirudo-dev/shirudo/issues/11>`__ records this limitation.

Process hardening.  ``util/harden.c`` runs before command dispatch in
both the core executable and ``shirudo-build``: ``PR_SET_DUMPABLE`` off,
``PR_SET_NO_NEW_PRIVS``, ``PR_SET_PTRACER`` cleared and ``RLIMIT_CORE`` zero.
``mlockall(MCL_CURRENT | MCL_FUTURE)`` keeps current and future mappings
out of swap for the process lifetime; failure is logged and refuses
startup. Sensitive buffers are scrubbed after use.
No host file may name code for it to load:
OpenSSL reads no configuration file, so none can activate a provider
module, and host names resolve through glibc's built-in ``files`` and
``dns`` services alone, so ``nsswitch.conf`` cannot add a module
either; ``/etc/hosts`` and ``/etc/resolv.conf``, a local resolver stub
included, still apply.  The zeroing allocator in ``util/malloc.c``
wipes freed memory; the libc allocators are poisoned project-wide.

Runtime and config enforcement. The UKI authenticates a runtime image mounted at
``/run/shirudo/runtime``; signed configuration is mounted separately at
``/run/shirudo/config`` with ``noexec``. Neither is the host root filesystem.
Every executable on the runtime image is equally eligible for authority.
``bprm_check_security`` stages the candidate decision and
``bprm_committed_creds`` commits it after successful exec. ``task_alloc``
inherits the mark. A failed exec leaves the current mark alone; a successful
outside-image exec clears it. Protected operations consult this mark rather
than mutable ``mm->exe_file``. ``PR_SET_MM`` cannot grant authority.

``bdev_setintegrity`` records metadata available through the existing
upstream hook. Device lookup checks the block-device pointer, device number
and disk sequence. Runtime records require the authenticated bootstrap root.
Config records require an authorized task and the expected root it staged
for that mapping. ``bdev_free_security`` attempts cleanup, but upstream
can omit the notification.
The ``file_ioctl`` and ``file_ioctl_compat`` hooks deny untrusted
callers mutating device-mapper control operations, including through old or
inherited FDs. This restriction applies to all DM devices on the target.
Trusted image tasks retain control access. These checks use existing LSM
hooks. Direct keyring access additionally requires the upstream
``KEY_SPEC_DM_VERITY_KEYRING`` API described in the requirements.
The metadata hook does not expose all verity options; complete mount-tree
protection remains unestablished. ``mmap_file`` and
``file_mprotect`` prevent trusted tasks from introducing host or anonymous
executable pages. Existing ptrace and process-memory checks still apply.

Writable state keeps its seal xattrs, while neither image receives seal
writes. The task mark authorizes writable-state and bpffs access.
The authorized BPF signing keys are enrolled at boot and the ``.bpf``
keyring then receives the existing reject-all restriction. A live config
update refuses a candidate requiring a signer absent from that sealed
keyring before measurement; new keys require boot-time enrollment and a
reboot. The existing key protection remains in place.

Image bundles use a standard verity superblock and a 64-character lowercase
SHA-256 root hash. The detached config signature covers exactly those ASCII
root bytes. The kernel verifies config signatures through its ``.dm-verity``
trust path, including built-in trusted keys. The trusted initrd enrolls the
bootstrap config certificate and seals the dedicated keyring. Runtime
acceptance instead requires the exact root authenticated by the UKI; a
valid config signature never grants executable authority.

Target image preflight validates the fixed verity format and exact backing
file sizes, creates or validates a strict read-only mapping and reads the
entire data device through kernel dm-verity before parsing contents. The
target has no userspace hash-tree implementation or external verifier.

Config activation verifies the candidate, persists its pending selection,
measures its root into the reserved static PCR, finishes key and mount
effects, then records completion. Its measurement log is separate from the
upatch NV register. Once pending, an interruption blocks further state
changes and config attestation until an operator reboots. The node keeps
running; Shirudo never triggers a reboot. Trusted startup verifies that
selection again, measures a fresh BOOT event and completes initialization;
it never retries the previous boot's PCR extension. The
`config-images <config-images.rst>`__ guide describes this flow and the
deferred TPM writer limitation.

The boot-scoped NV writer is separate from the operator's artifact key.
Trusted initialization creates its private key inside the TPM and freezes
its public modulus and the nonsecret 32-byte input needed to recreate it.
Each one-shot command checks the recreated key, signs the exact NV
extension and flushes the handle. The input is not an access control:
another process may recreate the key and ask the TPM to sign. The
``tpm_command`` LSM hook instead denies an untrusted ``TPM2_NV_Extend``
to Shirudo's selected NV index. The selected index is frozen during
initialization. Other TPM signing and PCR extension remain available.
A TPM reset in the same host boot keeps the writer identity; a TPM Clear
does not. `The TPM design <tpm.rst#write-policy>`__ describes the policy
and the remaining limits.

7) Target state
---------------

The authenticated initrd runs ``shirudo init`` before untrusted workloads.
The root service runs it again using the packaged runtime interpreter and
libraries. Both runs use the same enforcement and records; no fallback mode
exists. Initialization performs these steps:

1. Load authenticated bootstrap settings, including the runtime image root,
   then run prerequisite checks. Missing image settings are an error.
   ``--check-only`` stops before changing kernel state.
2. Bind ``/sysroot/var/lib/shirudo`` writable at its usual path in the initrd,
   so config selection and recovery can be recorded durably. Mount the private
   bpffs under ``/run/shirudo``.
3. Verify the runtime and selected config, enroll the config verification
   certificate in ``.dm-verity``, and seal it. Enroll the initial BPF certificate
   plus vouched config signers, less config revocations, in ``.bpf`` and seal it.
   Both enrollment boot parameters are required. A sealed empty BPF ring is an
   error, rather than a reason to stage keys in a user keyring.
4. Label writable state. Load both bootstrap BPF objects, populate and freeze
   their shared maps, seed bootstrap authority, attach device, mount and seal
   hooks, then attach the map-access and BPF admission gates last.
5. Mount the runtime under those guards, verify and measure the config
   selection, apply its revocations, and label state again to populate the
   inode protection cache. All image files stay read-only.
6. Restore the archived signed upatches in sorted order. Any failure leaves
   config completion pending and blocks changes and config attestation.
7. Bind this boot's upatch register and extend it once with
   ``SHA256("shirudo-init\0" || cert_sha256 || set_digest || tree_root)``.
   Append its event and mark config startup complete. The root service later
   adopts the pending initrd eventlog record without another extension.

Boot-restore extends the register by exactly one event however many
upatches it restores.  The register starts from zero at every boot, so
an operator predicts its value from the certificate and the installed
set alone (``shirudo attest predict``); no history is needed.  If any
re-apply fails the register is not written and ``status`` reports
``degraded``.  A re-run of ``init`` finds the register bound and on
record and leaves it alone, and restores nothing: an archived artifact
that is not loaded by then, which root can arrange by renaming a
signed artifact into the archive, is refused ``tampered`` rather than
attached without an event; one that finds the recorded register gone
refuses ``tampered`` until the next TPM reset.

Measurement register.  The measurement lives in a TPM 2.0 NV index
(default ``0x01818E00``) built the way systemd builds its NvPCRs: an
extend-only index (``TPM2_NT_EXTEND``) whose contents clear at every
TPM reset (``TPMA_NV_CLEAR_STCLEAR``) and whose write policy is
bound to PCRs 9 and 11 and the boot writer's public key.
Both the first and subsequent writes require command-bound authorization;
the complete policy is specified in `the TPM design <tpm.rst#write-policy>`__.
``init`` runs from the initrd,
after systemd has
measured ``enter-initrd`` into PCR 11 and before ``leave-initrd``
moves it, performs the first write through the PCR branch and then
extends PCR 9 with the record ``nvpcr-init:shirudo:0x1818e00:<name>``
(systemd's ``nvpcr-init`` format, ``<name>`` being the index's TPM
name), so that branch can never be satisfied again until the next
reset and nothing that runs after the initrd can bind at all; every
later extend presents the written branch.  An index undefined and
recreated at runtime therefore stays unwritable, and one recreated
under a weaker policy has a name other than the one ``init`` recorded
and anchored.  The record carries both PCR values and whether the
initrd was running, so a verifier pins the ``enter-initrd`` value and
refuses a binding made from the root file system.
Reads and certification use the index's empty authorization; no writer
secret is needed.  Defining and undefining the index need the owner
hierarchy.  Its authorization is empty by default; when set, the
password comes from ``tpm.owner_auth`` in
``/etc/shirudo/shirudo.conf``.  Every
state-changing command reads the register first and refuses with
``tampered`` when ``--expect-chain`` disagrees or the index is not the
one ``init`` recorded.  There is no TPM opt-out; an unmeasured target
is indistinguishable from a tampered one.

Eventlog.  ``/var/lib/shirudo/eventlog`` (mode 0600) holds one JSON
line per register extension: timestamp, boot ID, type (``init``,
``upatch_load``, ``upatch_unload``, ``tree_op``), the digest extended,
and the name and payload digest, the set digest or the tree operation.
The ``init`` record also carries the binding: the PCR value the policy
was computed from, the index name, the anchor record with its digest,
and the TPM's reset count, which tells one register period from the
next.  Replaying this boot's records from its ``init`` on must
reproduce the live value; ``shirudo status`` does that replay, checks
that the live index carries the recorded name, and reports ``Chain vs
eventlog`` and ``Anchored``.  When ``eventlog.max_bytes`` would be
exceeded, the operation refuses with ``eventlog_full`` before any load
or extend, so register and log never diverge.

Attestation.  ``shirudo attest --nonce=<hex>`` emits a JSON evidence
document: a ``TPM2_Quote`` over the SHA-256 bank (PCRs 0-7, 9 and
11-15 by default) and a ``TPM2_NV_Certify`` of the register, both
signed by the attestation key and carrying the nonce, the key's public
area and name, the PCR values, this boot's eventlog records, the
endorsement key certificate when the TPM holds one, and the firmware
and systemd measurement logs.  The attestation key is a restricted
P-256 ECDSA primary under the endorsement hierarchy with a fixed
template, so the same TPM always yields the same key; an operator
records its name once when enrolling the target.  ``shirudo attest
challenge`` makes a credential under the target's endorsement key for
that name, ``attest --challenge`` activates it in the TPM while
attesting, and ``verify --expect-credential`` checks the recovered
value, so the key is shown to sit in the TPM the endorsement
certificate describes instead of being taken on trust.  ``shirudo
attest verify`` on the operator checks the signatures and the nonce,
that the
quote covers the listed PCRs, that the certified index has the public
area a register bound to the recorded PCR value must have, that the
records replay to the certified value, that the anchoring PCR carries
the anchor, and that the register equals the value ``shirudo attest
predict`` computes from the certificate, the installed artifacts and
the tree root, or an ``--expect-chain`` the operator computed from
those plus the events since boot.  ``attest`` touches only the
target's TPM; ``verify`` and ``predict`` touch no TPM at all.

Files. Writable state under ``/var/lib/shirudo`` includes archived upatches,
eventlogs, locks, downloaded packages, tree state, cached images and the config
activation record. Initial BPF keys and bootstrap settings live in the runtime;
repository definitions, node labels, export settings, additional signer vouches
and revocations live in config. The operator keeps its private signing key
outside both images. Per-boot mounts and pins live under ``/run/shirudo``;
``eventlog.pending`` bridges the initrd and root service runs.

8) Packages and registries
--------------------------

A BPM package (``.bee``) is a gzip tarball with the ``Beefile``, the
built ``upatches/*.upatch`` and their unload directives, a
``README.md``, the signing ``cert.der`` and a ``build-environment.json``.
``shirudo bpm build <dir> --version <v>`` builds and signs every
``[[upatches]]`` entry through ``shirudo-build``.  ``shirudo bpm push
<pkg.bee> oci://host/ns/name`` uploads it as an OCI artifact
(``application/vnd.shirudo.bpm.package.v1+gzip``) with the certificate
as a referrer and, when given the signing material, adds the version to
the registry's detached-CMS-signed index at
``shirudo/bpm-index:stable``.  Published versions are immutable; an
index that already lists a version with other digests is refused.

Repository definitions and index verification certificates are prepared on the
operator and shipped in the signed config image.  ``shirudo bpm repo update`` fetches and verifies
the index; ``shirudo bpm install <name>/<pkg>[@ver]`` (or an ``oci://``
reference) pulls, verifies, unpacks and loads; ``upgrade`` moves
installed packages to the newest indexed version; ``uninstall`` loads
the package's unload directives; ``list`` and ``info`` inspect.
``shirudo bpm key`` manages the active certificate and refuses to switch
to a different one while a key is active.  The ``repo update`` and
``tree sync`` timers (60 s) and the map-export and keepalive timers
(5 s) are the only always-on infrastructure.

Repository definitions and verification certificates come
from the signed config. Local repository and key mutations refuse with
instructions for config activation or boot-time signer enrollment. The
package and tree update commands remain available. Repository ``key_file``
paths are confined to the held config image; tree signatures use the runtime
image's initial certificate. Node labels and the tree subscription also
come from the selected config. Config settings are validated before their
activation is measured.

upatch trees.  A tree is an append-only, globally ordered sequence of
``add`` and ``delete`` operations published as a CMS-signed JSON
document (``application/vnd.shirudo.upatch.tree.v2+json``), each
``.upatch`` pushed as an immutable OCI manifest.  Every operation
carries a selector (architecture, kernel release prefix, kernel build
ID, Kconfig values, node labels) that ``shirudo bpm tree sync``
evaluates locally against ``uname``, ``/sys/kernel/notes``,
``/proc/config.gz`` and ``/etc/shirudo/node.labels``; matching
operations apply in sequence order, each applied one is measured into
the register as a ``tree_op`` event (``SHA256("shirudo-tree\0" || seq
|| operation_digest)``), and the node's projection root enters the next
boot's ``init`` event.  ``shirudo bpm tree append <pkg.bee>
oci://host/repo [--op add|delete]`` publishes from the operator.  The
tree is enabled by ``/etc/shirudo/bpm/upatch-tree.conf`` and its timer;
without that file nothing changes.  The publication format is in the
format specification's companion section below.

Registry access honours ``BPM_OCI_SCHEME``, ``BPM_OCI_CA_FILE``,
``BPM_OCI_USERNAME``/``BPM_OCI_PASSWORD``, ``REGISTRY_AUTH_FILE`` and
``DOCKER_CONFIG``.  Every libcurl client in shirudo speaks TLS 1.3 with
a hybrid ML-KEM key exchange by default (X25519MLKEM768,
SecP256r1MLKEM768).  ``tls.classical_hosts`` in
``/etc/shirudo/shirudo.conf`` opts exact HTTPS DNS names into classical
key exchange, for example ``ghcr.io,quay.io``.  Operator commands read
this key from the root-managed host config; target commands read it only
from the immutable runtime image's config.  The list rejects wildcards
and IP addresses, and redirects are checked against each destination
host.  TLS 1.3 and certificate verification remain unchanged.  Shirudo
warns if an opted-in connection negotiates a non-hybrid group.  An empty
list requires hybrid exchange everywhere.  A classical exception
weakens transport confidentiality for that host, but signed publications
remain authenticated and cannot be forged by the registry, which can
still withhold or replay them.

Tree publication format.  The ``stable`` manifest has two layers, the
publication and its detached CMS signature.  The publication is::

    {"schema": 2, "tree_id": "...", "generation": N,
     "parent_manifest_digest": "sha256:...",
     "base": {"seq": 0}, "operations": [...], "head": {"seq": N}}

and each operation is::

    {"seq": N, "op": "add" | "delete", "id": "...",
     "selector": {...},
     "artifact": {"repository": "...", "manifest_digest": "sha256:...",
                  "layer_digest": "sha256:...", "payload_sha256": "..."},
     "operation_digest": "..."}

where ``operation_digest`` is the SHA-256 of the compact JSON of the
same object without that field, with selector keys and list values
sorted.  ``tree append`` fetches and verifies the current publication
(a missing one starts generation 1 with the package name as tree id),
pushes each artifact as a manifest tagged ``upatch-<id>-<payload16>``,
appends one operation per entry with ``seq = head + 1``, and
republishes with ``generation + 1`` and ``parent_manifest_digest`` set
to the manifest it replaced.  A publication with a number outside the
signed 64-bit range, or a ``generation`` or ``head`` at its top that
leaves no successor, is refused.  A ``delete`` publishes the entry's
unload directive and is accepted by a target only for an id it loaded
from the same tree.

9) Observability
----------------

``shirudo status`` reports the machine it runs on: roles, version ID,
the conditions ``LsmAttached``, ``KeyringSealed``, ``ChainIntact`` and
``TpmMeasured`` with an ``OK``, ``WARN`` or ``ALERT`` verdict each, the
keyring serial against its pin, the register against this boot's
eventlog replay and its anchor, the on-disk assets, and with
``--include-system``, ``--include-eventlog``, ``--include-kernellog``
and ``--include-modules`` the corresponding detail.  The register is
always read: a status that did not ask the TPM would be a status the
target wrote about itself.  The overall
``status`` is ``ok``, ``degraded``, ``init-pending``, ``lsm-off`` or
``tampered``.  ``--json`` emits the same as one document; ``--otel``
pushes it as a keepalive log record.  ``status`` is the target's own
account of itself; ``shirudo attest`` (section 7) is the account the
TPM signs.

``shirudo upatch list``, ``info``, ``get`` and ``map`` inspect
artifacts and loaded state.  ``info`` describes the container offline,
signed decoders included, and is advisory; ``get`` reads the loaded
program's ``line_info`` and BTF from the kernel and is authoritative.
``upatch map`` reads pinned maps, runs the upatch's signed Lua decoder,
and prints, appends NDJSON, or exports over OTLP.  The export path, its
decoders and the collector integration are described in
`telemetry <telemetry.rst>`__.

Every command logs through ``syslog(3)`` as ``shirudo`` to
``LOG_AUTHPRIV``; ``journalctl -t shirudo`` shows it.

10) Failure reporting
---------------------

``upatch load`` and ``upatch unload`` take ``--report=<path>`` and write
one JSON document: ``result``, the ``phase`` reached (``pre_flight``,
``parse``, ``signed_loader_load``, ``payload_load``, ``link_create``,
``pin``, ``persist``, ``tpm_extend``, ``done``), ``errno`` and its
name, a ``category``, a message, the verifier log when the verifier
spoke, the loader's return value, the artifact's path and name, the
kernel release, and the NV index and chain value after the operation.

The categories are ``ok``, ``tampered``, ``keyring_missing``,
``lsm_denied``, ``signature_rejected``, ``signature_unsupported``,
``verifier_rejected``, ``parser_rejected``, ``btf_mismatch``,
``attach_target_missing``, ``binary_mismatch``,
``attach_scope_mismatch`` (the link the kernel made is not at the site
the metadata names: another cgroup, network namespace or PMU),
``payload_mismatch``, ``already_unloaded``, ``detach_failed``,
``tpm_error``, ``eventlog_full``, ``kernel_abi_unsupported``,
``init_prereqs_missing``, ``version_mismatch`` and ``unknown``.
Automation treats ``tampered`` as "refresh state, then decide", never
as "retry the same input": a concurrent legitimate operator produces
it too.

11) Runtime design
------------------

The core binary never forks or execs; the one exception is the
operator-only ``shirudo build`` dispatch described above.  Everything
else is a library call or a syscall: libbpf for BPF, raw ``keyctl``
for keyrings, tpm2-tss for the TPM, libcrypto for digests and
certificate parsing, libcurl over libssl for registries and OTLP,
libelf and zlib for objects, LuaJIT for decoders.  The in-tree
``util/json.c`` is the only JSON code and ``util/parse-options.c`` the
only option parser.  Nothing else is linked; every additional library
is attack surface.

Both profiles need OpenSSL 3.5 or newer for ML-DSA.  The operator links
the system shared libraries.  The target image (``make target``) links
a static OpenSSL, an OpenSSL-backed static libcurl and a static tpm2-tss
that ``make target-deps`` builds from source, plus static libbpf,
libelf, zlib, zstd and LuaJIT, so it runs on a
distribution whose OpenSSL predates ML-DSA.  ``SHIRUDO_VERSION_ID``
hashes the source tree and build configuration, not binary bytes, so
the same source yields the same identity on x86-64, arm64 and riscv64;
the pre-flight refuses a ``version_mismatch``.

shirudo requires the signed-loader and BPF LSM interfaces in the validated
upstream development kernel and current upstream clang. The `requirements
<requirements.rst>`__ document identifies the tested bpf-next commit and
configuration. The signed-loader ABI check, rather than a release string,
rejects incompatible kernels; missing features fail the build or pre-flight.

13) Kernel work this design waits for
-------------------------------------

Several residual risks in the threat model are closed by kernel work in
flight rather than by shirudo code:

- the signed loader creating the link and pinning it, and detaching
  and unloading in kernel, so the whole lifecycle is signature-covered
  (residual risk 1);
- BPF in-kernel sockets, so keepalive, status and alerting can be sent
  from kernel context without a userspace timer;
- xattr getters for kernfs, so ``security.bpf.*`` labels can be
  enforced on cgroups;
- ``fmod_ret`` coverage of the whole kernel build, so a shield can
  reject a call at any function rather than at the instrumented ones;
- signed-loader support for every program type, including struct_ops.

shirudo tracks the current upstream kernel; when one of these lands,
the corresponding shirudo change follows and the residual is removed
from the threat model.
